## 1. 它到底在干什么

你的实例 `D:\Minecraft\.minecraft\versions\ODF-JustAero` 里有 244 个 jar、900 多 MB。

普通做法是把它压成一个 zip 发出去。这个项目不这么做，它做的是：

```
读实例 → 算出每个 jar 的 sha1/sha512 → 拿哈希去问「这个 jar 是谁发布的、从哪下」
       → 写成一堆 .pw.toml（每个文件一段「来源 + 哈希」的声明）
       → packwiz 把这些声明编译成 index.toml（一份 sha256 总清单）
```

于是仓库里**没有 jar**（除了 6 个确实没地方下的），只有「从哪下、下载完应该是什么哈希」。

**这样做的好处**

- 仓库只有 ~60 MB，推送秒完成
- 玩家拿到的是**原作者的 jar**，不是你的二次分发
- 作者更新了，`packwiz update` 能跟
- 输出标准 `.mrpack`，Prism / Modrinth App / ATLauncher / MultiMC 都能直接导入

**这样做的代价**

- 玩家第一次安装要联网下载 ~900 MB（和传统包一样）
- 某个 mod 从 CDN 下架了，链接就失效了（脚本的核对会告诉你）
- 有 6 个 mod 找不到来源，只能随包附带

## 2. 一次性准备

### 2.1 需要装的东西

| 工具 | 用途 | 检查命令 |
|---|---|---|
| Python 3.9+ | 跑提取脚本 | `py -3 --version` |
| git | 版本管理 | `git --version` |
| GitHub CLI `gh` | 拉 packwiz 二进制、建仓库 | `gh auth status` |

没有 `gh` 的话：`winget install GitHub.cli`，然后 `gh auth login`。

### 2.2 改实例路径

打开 **`tools/settings.ps1`**，这是**唯一需要你编辑的文件**：

```powershell
$InstancePath = 'D:\Minecraft\.minecraft\versions\ODF-JustAero'
```

如果你以后重命名了实例文件夹，改这一行就行，其他脚本都从这里读。

### 2.3 抓二进制

```powershell
.\tools\Get-Tools.ps1
```

它会往 `tools\bin\` 放三个文件（这个目录**不进 git**，所以别人 clone 后要自己跑一次）：

| 文件 | 来源 | 说明 |
|---|---|---|
| `packwiz.exe` | GitHub Actions 构建产物 | **packwiz 官方没有 Release**，只有 CI 产物 |
| `packwiz-installer.jar` | 官方 Release | 安装器 |
| `packwiz-installer-bootstrap.jar` | 官方 Release | 玩家双击的就是它 |

> 没有 `gh` 怎么办：`go install github.com/packwiz/packwiz@latest`，
> 或者去 <https://nightly.link/packwiz/packwiz/workflows/go/main> 手动下载。

## 3. 日常流程：改完整合包之后

你平时的动作是「打开启动器 → 加个 mod → 进游戏玩」。玩爽了要发布，就一条命令：

```powershell
.\tools\Update-Pack.ps1 -Bump -Push
```

这一条命令做了 5 件事：

| 步骤 | 做什么 |
|---|---|
| 1/5 | 读实例，重新解析 244 个 jar → **wifi** 重建 `pack\` |
| 2/5 | `packwiz refresh` 规整 `index.toml` |
| 3/5 | 出审计报告：哪些 mod 有新版本了（`pack/audit-report.txt`） |
| 4/5 | 核对：仓库和实例还一致吗（`pack/verify-report.txt`） |
| 5/5 | git commit + push |

推送之后 **GitHub Actions 自动**：规整索引 → 生成 `.mrpack` → 传成 artifact → 更新 Release。

> ⚠️ `pack\` 是**整目录删除重建**的，所以不要手动往 `pack\` 里放东西。
> 你的**游戏实例永远不会被修改**，脚本只读它。
> 想先看看会发生什么：加 `-DryRun`。

## 4. 三个脚本的完整参数

### 4.1 `tools\Update-Pack.ps1` —— 主流程

```powershell
.\tools\Update-Pack.ps1 [参数]
```

| 参数 | 作用 |
|---|---|
| `-Instance <路径>` | 临时指定实例，覆盖 `settings.ps1` |
| `-Version 0.6.0` | 指定版本号 |
| `-Bump` | 版本号补丁位 +1：`0.5.0` → `0.5.1` |
| `-SkipAudit` | 不生成「有新版本」报告 |
| `-SkipVerify` | 不核对（**不建议**）|
| `-SkipUrls` | 核实时不检查下载链接是否还有效（快很多）|
| `-DryRun` | 只显示计划，不写文件 |
| `-Commit` | 提交（不推送）|
| `-Push` | 提交并推送（隐含 `-Commit`）|

常见组合：

```powershell
# 只想看看现在和实例差在哪
.\tools\Update-Pack.ps1 -DryRun

# 重建但先不提交，自己 review
.\tools\Update-Pack.ps1

# 正式发版
.\tools\Update-Pack.ps1 -Bump -Push
```

### 4.2 `tools\Verify-Pack.ps1` —— 只核对，不改动

```powershell
.\tools\Verify-Pack.ps1 [-Instance <路径>] [-SkipUrls]
```

返回码 **0 = 全部通过**，非 0 = 有问题。可以直接当 CI 门禁用。

核对 9 项：

| # | 检查 |
|---|---|
| 1 | 游戏版本 / 加载器版本是否一致 |
| 2 | `index.toml` 里每个文件都在，sha256 都对 |
| 3 | 实例里每个 jar 都被覆盖到了（没有漏的、没有多的）|
| 4 | 记录在案的下载哈希 == 你本地实际跑的字节 |
| 5 | 随包附带的 jar 和实例里的完全一致 |
| 6 | 实例里有没有重复 modId（同一个 mod 装了两份）|
| 7 | 客户端 / 服务端标记 |
| 8 | `config` / `resourcepacks` / `options.txt` 是否对齐 |
| 9 | 每个下载链接还能不能打开 |

> 第 6 项曾经真的抓到问题：实例里同时装着 `lithostitched-1.8.0` 和 `1.8.1`，
> 两个都声明 `modId = lithostitched`。

### 4.3 `tools\Export-Mrpack.ps1` —— 生成 .mrpack

```powershell
.\tools\Export-Mrpack.ps1 [-Out <文件>] [-RestrictDomains] [-NoRefresh]
```

| 参数 | 作用 |
|---|---|
| `-Out` | 输出路径，默认 `dist\ODF-JustAero-<版本>.mrpack` |
| `-RestrictDomains` | 只允许 Modrinth 白名单域名（投稿模式，会拒绝 CF 来源的文件）|
| `-NoRefresh` | 跳过 refresh |

**第一次会慢**：packwiz 要把 238 个文件各下载一次来记录体积，
约 900 MB、3 分钟左右，进 `.packwiz-cache\`。**之后秒出。**

### 4.4 `tools\packwiz_from_instance.py` —— 核心解析器

平时不用直接调，但知道这些开关有用：

```powershell
py -3 tools\packwiz_from_instance.py --instance <实例> --out <目录> [参数]
```

| 参数 | 作用 |
|---|---|
| `--instance` `--out` | 实例路径 / 输出目录（**必需**）|
| `--name` `--author` `--version` | 写进 `pack.toml` |
| `--mc` `--loader` `--loader-version` | 覆盖自动探测的游戏版本 |
| `--old-index <zip/json>` | 用旧 `.mrpack` 的哈希表当第二数据源 |
| `--include <条目>` | 额外复制实例根目录的某项（可重复）|
| `--exclude-glob <通配>` | 跳过匹配的路径（可重复）|
| `--keep-caches` | 不剔除缓存目录（默认会剔）|
| `--no-options` | 不打包 `options.txt` |
| `--include-disabled` | 把 `.jar.disabled` 作为「默认关闭的可选 mod」带进去 |
| `--no-cf-search` | 跳过 CurseForge 按文件名匹配（更快）|
| `--no-bundle` | 解析不到的 jar 不随包附带 |
| `--jobs N` | 并发数 |
| `--cache <json>` | CurseForge 查询缓存 |
| `--report <txt>` | 提取报告 |
| `--force` | **允许清空输出目录**（会被脚本自动带上）|
| `--dry-run` | 只显示计划 |
| `--audit` | 构建完顺便生成更新审计 |
| `--audit-only` | 不构建，只审计已有包（只读）|
| `--audit-cross` | 审计时额外去 Modrinth 搜 CF 源的 mod（慢，启发式）|
| `--verify` | 不构建，只核对已有包（只读）|
| `--check-urls` | 配合 `--verify`，额外检查每个下载链接 |

## 5. GitHub Actions 自动打包

`.github/workflows/build-mrpack.yml`

**触发条件**

| 时机 | 行为 |
|---|---|
| push 到 `main` | 生成 `.mrpack`，更新 `v<版本>` 这个 Release |
| 手动 `workflow_dispatch` | 同上，可选 `update_mods` 先升所有 mod |
| 每周一 03:17 UTC | 重新构建，让 Release 跟得上仓库 |

**为什么不能让 Actions 直接从实例提取？**

因为 Actions 跑在 GitHub 的机器上，**看不见你电脑里的实例**。所以顺序必然是：

```
你的实例 → (本地) Update-Pack.ps1 → git push → Actions 打包 → Release
```

想要「实例一变就自动」的话，用 Windows 任务计划定时跑 `Update-Pack.ps1 -Bump -Push` 就行。

**产物在哪**

- Actions 页面 → 对应 run → Artifacts
- 或者 Release 页面直接下 `.mrpack`

Release 的下载链接是稳定的：

```
https://github.com/OnDreamQwQ/ODF-JustAero-Pack/releases/latest/download/ODF-JustAero-<版本>.mrpack
```

## 6. 把包发给别人

### 方式 A：`.mrpack`（推荐）

让对方去 Release 下载 `.mrpack`，然后在启动器里：

- **Prism Launcher**：Add Instance → Import from file → 选 `.mrpack`
- **Modrinth App**：Add Instance → Import from file
- **ATLauncher / MultiMC**：同理，都有 import

### 方式 B：packwiz 自动更新（改一次，所有人跟着更新）

玩家只需要一个 `packwiz-installer-bootstrap.jar`：

```bash
java -jar packwiz-installer-bootstrap.jar https://raw.githubusercontent.com/OnDreamQwQ/ODF-JustAero-Pack/main/pack/pack.toml
```

放进 Prism 的「Pre-launch command」（Java 参数那栏旁边），
之后每次启动都会自动增量更新。

> 这两个方式都要求仓库是**公开**的。私有仓库玩家拿不到 raw 链接。

## 7. 排错手册

这些都是**实际踩过的坑**，原样记下来。

### `failed to create cache directory: mkdir C:\Users\...\AppData\Local\packwiz: Access is denied.`

packwiz 默认缓存目录建不出来。**所有脚本都已经处理了**（统一用仓库下的
`.packwiz-cache`）。如果你手动敲 packwiz，记得加：

```powershell
packwiz.exe --cache .\.packwiz-cache modrinth export ...
```

### `open pack.toml: The system cannot find the file specified.`

packwiz 必须在**包根目录**里跑：

```powershell
cd pack
..\tools\bin\packwiz.exe list
```

### PowerShell 里命令明明成功了，`$LASTEXITCODE` 却是 1

加了 `2>&1` 就会这样（stderr 被当成错误记录）。**别加 `2>&1`**。

### `gh api ... --jq '带空格的表达式'` 报 `accepts 1 arg(s), received 5`

PowerShell 把空格拆开了。改成管道：

```powershell
gh api repos/... | ConvertFrom-Json
```

### `packwiz.exe` 下载不到 / Releases 页是空的

**packwiz 官方就是不发 Release**。只能从 Actions 产物拿：

```powershell
.\tools\Get-Tools.ps1
```

或者 `go install github.com/packwiz/packwiz@latest`。

### 导出 `.mrpack` 卡在 `Retrieving 238 external files...`

正常现象。packwiz 要下载每个文件记录体积，第一次 ~900 MB / 几分钟，之后就快了。
**别中断**，中断会留下半个缓存。

### 核对报告里的 `PROBLEM`

`pack/verify-report.txt` 里以 `PROBLEM` 开头的行就是不一致的地方。
最常见的是「同一个 modId 装了两份」——去实例的 `mods\` 把旧的那份
改名成 `.jar.disabled`，然后重跑 `Update-Pack.ps1`。

### 我改了某个 mod 的 jar 文件（比如打了补丁）

脚本会按哈希去查来源，发现**字节对不上**，于是把这个 jar **随包附带**，
并在报告里写 `name matched but bytes differ, bundling instead`。
这是正确行为——它不会用一个 CDN 上的「同名但不同内容」的文件来冒充你的版本。

## 8. 原理：一个 mod 是怎么被认出来的

对每个 jar 算 sha1，然后按顺序问四个数据源，**先命中的赢**：

| 顺序 | 数据源 | 命中后写入 |
|---|---|---|
| 1 | `POST https://api.modrinth.com/v2/version_files`（sha1 精确匹配，**不需要 API key**）| `[update.modrinth]` + `cdn.modrinth.com` 下载链接 |
| 2 | 旧 `.mrpack` 的哈希表 | `mediafilez.forgecdn.net` 下载链接 |
| 3 | CurseForge（社区镜像 `api.curse.tools`，**只接受文件名完全相等**）| `[update.curseforge]` |
| 4 | 都查不到 | **随包附带**这个 jar |

**第 3 步为什么必须「文件名完全相等」？**
因为 CurseForge 的指纹接口从这台机器调不通（官方要 API key，社区镜像没代理这个
POST 接口）。退而求其次用文件名搜，一旦模糊匹配就会把「同名但版本不同」的文件
写成你的来源，玩家装出来就是另一个版本。所以宁可附带，也不猜。

**为什么 sha512？**
Modrinth / CurseForge 的元数据里记的是 sha512（只有本地文件走 sha256）。
这是 packwiz 的惯例，不是 bug。

**本项目的 244 个 mod 实际分布**

| 来源 | 数量 |
|---|---|
| Modrinth | 203 |
| CurseForge | 23 |
| 无更新元数据（只有直链）| 14 |
| 随包附带 | 6 |

## 9. 关于授权与再分发

这一节很重要，因为**「能装」和「能发」是两件事**。

### 9.1 Modrinth 的两道关

| 关卡 | 这个包 |
|---|---|
| **域名校验**：只允许 `cdn.modrinth.com` / `github.com` / `raw.githubusercontent.com` / `gitlab.com` | ❌ 33 个文件是 `forgecdn.net`，**过不了** |
| **授权审查**：非 Modrinth 托管的内容要逐个举证授权 | 没有走这一步 |

所以要**投稿到 Modrinth**，得先处理那 33 个 CF 独占的 mod（换 Modrinth 版本、
或者提供授权证明）。**自己用 / 发网盘 / 发 GitHub Release 不受此限制。**

### 9.2 那 6 个随包附带的 jar

`create_flight_control`、`createredstonelinkgui`、`createrenxin`、`neo-voxy`、
`simurail`、`sable…`（以 `verify-report.txt` 的 D 区为准）。

随包附带 = **你在再分发**。公开分享前请确认它们的许可证允许。
不确定就把仓库设成私有，只发 Release 里的 `.mrpack` 给朋友。

### 9.3 CurseForge

CF 的授权范围是「通过 CF 分发的整合包」。把 CF 的 jar 搬到 GitHub 上给别人用，
**出了这个范围**。如果以后想投稿 CF，注意它要求「必须用 CF App 生成、不许手改 manifest」，
这个项目的工作流不满足。

## 10. 命令速查

```powershell
# ---- 准备 ----
.\tools\Get-Tools.ps1                    # 抓 packwiz 等二进制

# ---- 日常 ----
.\tools\Update-Pack.ps1                  # 从实例重建（不提交）
.\tools\Update-Pack.ps1 -DryRun          # 只看计划
.\tools\Update-Pack.ps1 -Bump -Push      # 重建 + 版本+1 + 推送

# ---- 检查 ----
.\tools\Verify-Pack.ps1                  # 完整核对（含链接）
.\tools\Verify-Pack.ps1 -SkipUrls        # 快速核对

# ---- 打包 ----
.\tools\Export-Mrpack.ps1                # 生成 .mrpack

# ---- 直接操作 packwiz ----
cd pack
..\tools\bin\packwiz.exe --cache ..\.packwiz-cache list          # 列出所有 mod
..\tools\bin\packwiz.exe --cache ..\.packwiz-cache update --all  # 升级所有 mod
..\tools\bin\packwiz.exe --cache ..\.packwiz-cache serve         # 本地起服务器测试

# ---- 玩家安装 ----
java -jar packwiz-installer-bootstrap.jar https://raw.githubusercontent.com/OnDreamQwQ/ODF-JustAero-Pack/main/pack/pack.toml
```

## 附：审计报告怎么看

`pack/audit-report.txt` 分五区：

| 区 | 含义 | 你该做什么 |
|---|---|---|
| **A** | Modrinth 上有新版本 | 想升就 `packwiz update <名字>`；`jei` 这种 beta 慎升 |
| **B** | CurseForge 上有新版本 | 同上 |
| **C** | 没有更新元数据，`packwiz update` **会跳过** | 只能手动换 |
| **D** | 随包附带的 jar | 每次都要自己保证有权分发 |
| **E** | 跨平台候选（`--audit-cross` 才生成）| 启发式，仅供参考 |

A 区里「大版本跳跃」和「pre-release」要格外小心：
整合包最怕的就是某个 mod 从 `0.6` 跳到 `0.7` 把 Create 的配方全打乱。
**升级前先在测试实例里跑一遍。**
